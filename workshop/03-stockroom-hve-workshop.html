Stockroom HVE Workshop
HVE Core · Module 3 · Hands-on

From an ambiguous request to sprint-ready work, with HVE Core and the Stockroom inventory app

A one-day team workshop in which product and engineering roles use HVE Core's agents and prompts, inside VS Code and GitHub Copilot, to carry one real feature request — staff accounts and sign-in for the open-source Stockroom small-business inventory & POS app — through Discovery, Product Definition, Decomposition and Sprint Planning. Every phase is done by several roles in parallel, then reviewed, reconciled and approved before it becomes the next phase's input. The backlog lives in Azure DevOps; the code lives in a shared GitHub fork.

Section 01

Module overview

Most AI-assisted engineering fails before code is written: a vague request goes straight to an implementation prompt, the assistant fills the gaps with plausible guesses, and the team discovers the missing requirements in review. This module fixes the front half of the lifecycle. You will take one deliberately ambiguous request — "people need to sign in" — and turn it into evidence-based, traceable, sprint-ready work that both humans and AI coding agents can execute with little ambiguity.

What you practise

  • Investigating a problem before solving it (Design Thinking coaching + repository research)
  • Writing requirements a test can verify (EARS + Given/When/Then)
  • Recording architecture decisions as ADRs
  • Decomposing a PRD into an Azure DevOps work-item hierarchy with dependencies
  • Planning a sprint against capacity and risk

How you work

  • Each phase runs in parallel across five roles
  • Every role uses HVE agents directly (the Product Owner is not a question-answering service)
  • Outputs are reconciled through a shared branch, PR review and an approval gate
  • Only an approved baseline moves to the next phase

What you leave with

  • A BRD, a PRD, three ADRs and a prioritised ADO backlog for a real Stockroom feature
  • A reusable Parallel → Evidence → Review → Reconcile → Approve → Baseline pattern
  • A prompt library and command reference you can reuse on your own repositories

Why this application

Stockroom is deliberately small: one Python file, seven templates, two tables, no tests, no authentication. That is the point. In a 372-line codebase nobody can hide behind "the repo is too big to check" — every claim an agent makes can be verified against a file and a line number in under a minute, so the workshop can be about process discipline rather than archaeology. The feature you add (staff accounts and sign-in) is also small enough to decompose completely in one day, yet it forces real decisions: session mechanism, password storage, first-run bootstrap, roles, schema migration on an existing SQLite volume.

How Design Thinking and RPI fit in

Design Thinking (DT) — problem before solution

Fact dt-coach guides nine methods across three spaces: Problem (1 Scope Conversations, 2 Design Research, 3 Input Synthesis), Solution (4–6), Implementation (7–9). Session state lives in .copilot-tracking/dt/{project-slug}/. The Problem Space exit produces a handoff with assumptions carrying validated / assumed / unknown confidence markers that task-researcher consumes.

Decision In this workshop we use Method 1 (Scope Conversations) — and optionally Methods 2–3 (Design Research, Input Synthesis) — during Discovery only.

RPI — Research, Plan, Implement, Review

Fact In the released HVE Core (3.3.x) RPI is four phases, each owned by its own custom agent and reached by a prompt that switches to it: /task-research topic=… → Task Researcher (.copilot-tracking/research/{date}-{topic}-research.md), /task-plan research=… → Task Planner (plan + details files), /task-implement → Task Implementor, /task-review → Task Reviewer. HVE's rule: always /clear or start a new chat between phases; findings live in files, not chat. The autonomous rpi-agent (/rpi task=…) runs a fifth phase, Discover, that proposes follow-up work — do not confuse it with lifecycle Stage 2 "Discovery".

Decision We use /task-research for repository evidence in Discovery and for dependency analysis in Decomposition, and /task-plan to build the evidence-based implementation plan in Sprint Planning; implementation and review belong to Module 4.

Which HVE Core you actually have

Fact The VS Code Marketplace extension ise-hve-essentials.hve-core (3.3.x) ships only the flagship RPI collection (rpi-agent, task-researcher, task-planner, task-implementor, task-reviewer, memory, doc-ops, prompt-builder, pr-review and subagents). brd-builder, prd-builder, adr-creation, dt-coach, security-planner, ado-backlog-manager and ado-prd-to-wit live in separate collections (hve-project-planning, hve-design-thinking, hve-security, hve-ado) or in the all-in-one ise-hve-essentials.hve-core-all extension. Section 04

Stockroom Inventory scenario

Stockroom is a small-business inventory and sales (point-of-sale) web application. A shop keeps its product catalogue in it, records every sale at the counter, watches which items are running low, and reads simple revenue reports. You are playing the product team of a small stationery shop in Dhanmondi, Dhaka that has adopted Stockroom on a shared counter laptop and a tablet, and now needs to extend it. The app is open source (pangwanabervely-stack/stockroom-inventory-app) and deliberately small, which is what makes it a good workshop subject: every claim about it can be checked in minutes.

Major business capabilities

Dashboard

One screen for the owner: how many products are on the books, what the stock is worth, total revenue to date, which items have fallen below their reorder level, and the last few sales.

Product management

Add, view, edit and remove products — name, SKU, category, quantity in stock, reorder level, unit price and supplier — with a search box and checks that stop duplicate SKUs and nonsense numbers.

Recording sales

At the counter, pick a product and a quantity; Stockroom works out the total at today's price, refuses to sell more than is on the shelf, and takes the sold items off the stock count in one step.

Sales history

The full ledger of every transaction, newest first — what was sold, how many, at what price, and when.

Reports

Which products earn the most, and how revenue splits across categories — the numbers the owner uses to decide what to reorder and what to drop.

What it does not have

No accounts, no sign-in, no roles, and no record of who did what. Anyone who can reach the screen can change anything. The app's own documentation lists this as its first known limitation.

Technology stack

Stockroom is a conventional server-rendered web application. The client — a browser on the shop's counter laptop or tablet — talks over HTTP to the Stockroom app, which is itself three layers: presentation, application and data. Nothing exotic sits between the person at the counter and the data, which is why the feature you will add touches every layer and why the team can reason about it end to end in one day.

The reusable collaboration pattern

Every lab in this workshop follows the same shape. It is the single most important idea in the module.

Parallel work→Evidence→Review→Reconcile→Approve→Baseline→Next phase

Parallel work

Each role investigates its own concern with its own HVE agent, on its own branch and in its own file. Nobody waits for anyone else.

Evidence

Every finding is tagged Fact / Assumption / Decision and cites its source (file path and line, interview, doc). AI output is evidence to be checked, not truth.

Review

Findings are read by at least one other role via pull-request comments. Reviewers look for conflicts, duplicates, undefined terms and unverified claims.

Reconcile

The phase owner merges findings into one artifact using the reconciliation prompt, resolves conflicts explicitly in a decision log, and unifies terminology in the glossary. Section 12 is the playbook.

Approve

A named human approves against the exit criteria. AI never approves. Unresolved items go to an "open questions" table with an owner, not into silence.

Baseline

The approved artifact is merged to main under docs/. From now on it is the input of record; changes require a new PR.

Part A — from ambiguous to testable

Weak

Users should log in before using the app.

Improved

When a request for any page other than the sign-in page arrives without a valid signed-in session, the system shall redirect to the sign-in page and, after successful sign-in, return the person to the page they requested.

The improved version is executable by a developer and by an AI coding agent because it names: a concrete trigger (a request without a valid session), an explicit exception (the sign-in page itself), and two observable responses that a test can check (redirect; return to the original page). Nothing in it says how the session is kept, which is left to ADR-001. Workshop recommendation EARS (Ubiquitous / Event-driven "When…" / State-driven "While…" / Unwanted-behaviour "If… then…" / Optional-feature "Where…") and Given/When/Then are widely used requirement syntaxes; HVE 3.3's prd-builder does not mandate them, so we ask for them explicitly in every prompt. Rules we enforce: one response per statement, name the trigger concretely, no unquantified adjectives, observable responses only.

Weak

Passwords must be secure.

Improved (NFR + unwanted behaviour)

NFR-001 The system shall store only a salted, adaptive one-way hash of each password; the plain text shall never be written to the database or to logs. FR-00x If a sign-in attempt fails, then the system shall show the same message whether the username or the password was wrong.

Weak

Cashiers can't see reports.

Improved (EARS unwanted behaviour)

FR-00x If a signed-in cashier requests the Reports page, then the system shall respond with "not allowed" (HTTP 403) and shall not include any revenue figures in the response.

Part B — decisions the PRD must not make

A PRD that says "use a session cookie with a users table" has decided architecture without evidence. Fact adr-creation coaches Socratically, drafts in .copilot-tracking/adrs/{topic}-draft.md and finalises to docs/decisions/YYYY-MM-DD-{topic}.md with context, stakeholders, constraints, weighted decision drivers, alternatives, decision and consequences; system-architecture-reviewer evaluates designs against Well-Architected areas and checks alignment between ADRs. Three decisions are run in parallel by three pairs, then cross-reviewed for consistency.

ADR-001 Session & request guard

Options: (a) Flask's built-in signed session + a before_request guard with an allow-list of public endpoints; (b) the Flask-Login extension; (c) per-view decorators only. Drivers: no new dependency without justification (NFR-C4), single-module structure, "every route is protected" must be provable by one test. Example decision (a).

ADR-002 Credential storage & first-run bootstrap

Options for storage: Werkzeug generate_password_hash (scrypt/pbkdf2) vs a new library. Options for bootstrap: (a) a one-time /setup page shown only while the users table is empty; (b) an environment variable read at startup; (c) a CLI command. Drivers: non-technical owner on Docker, BR-007, no shell access. Example decision Werkzeug hashing; bootstrap via (a), with (c) as the documented recovery path.

ADR-003 Authorisation model & schema change

Options: two fixed roles stored on the user row with a manager_required decorator, vs a permissions table. Plus the schema question: add users with CREATE TABLE IF NOT EXISTS and add sales.recorded_by with an idempotent ALTER TABLE guarded by PRAGMA table_info. Drivers: BR-003, ≤ 10 accounts, upgrade of an existing volume (NFR-C2). Example decision fixed roles; guarded ALTER in init_db().

# ADR-001 Signed session + before_request guard for staff sign-in
Status: Accepted · Date: 2026-09-17 · Owners: Architect, Developer

## Context
Stockroom is one Flask module with eight routes (app.py:74–356) and a signed cookie session
already configured for flash messages (app.py:15) [Fact]. FR-001 requires every page except
an allow-list to redirect unauthenticated requests; FR-005 requires a disabled account to lose
its session at its next request; NFR-003 requires a single test to prove coverage; NFR-C4
forbids new dependencies without justification [Fact: copilot-instructions.md].

## Decision drivers (weighted)
- Provable "every route is protected" (NFR-003) — High
- No new dependency; fits the single-module style — High
- Disabled-account check on every request (FR-005) — High
- Familiarity for future contributors — Medium

## Options
A. Built-in session + @app.before_request guard with PUBLIC_ENDPOINTS = {"login","setup","static"};
   the guard loads the user row into flask.g (same pattern as get_db, app.py:23) and refuses
   inactive users — meets all drivers; we own ~25 lines.
B. Flask-Login — mature, but adds a dependency, uses per-view @login_required (coverage must be
   audited route by route), and FR-005 still needs a custom user_loader check.
C. Per-view decorators only — a forgotten decorator silently exposes a route; violates NFR-003.

## Decision
Option A. The guard runs first; ADR-003's manager_required check runs inside the view after
g.user is set. SECRET_KEY is read from the environment (NFR-002); the historical default is
rejected unless FLASK_DEBUG is on.

## Consequences
+ One test iterating app.url_map proves NFR-003; disabled users are cut off on the next request.
− We maintain the allow-list; adding a public route requires touching it (documented in
  copilot-instructions.md). − Existing smoke test test_dashboard_renders must sign in first.
Related: ADR-002 (how the user row is verified), ADR-003 (role check placement).

Section 12 Collaboration

Reconciling role artifacts for the next step

Every lab produces several files written by different people with different agents, and the next lab consumes exactly one artifact of record. This section is the playbook for turning many into one: the meeting, the agent prompt that prepares it, the decision log that records it, and the gate that closes it. It is the same five steps in every phase; only the phase owner, the agent and the artifact change.

The five steps of collaboration

1 · Merge
Collect
Phase owner merges every contributor branch into <phase>/reconciled. Different files → no conflicts. Nothing is edited yet.
2 · Agent
Prepare
Run the phase's reconciliation prompt. The agent lists conflicts, duplicates, terminology drift, unverified claims and unowned questions — and waits. It does not decide.
3 · Meeting
Decide
15–20 min, facilitated by the Scrum Master. Walk the five lists item by item. Each item ends with a decision, an owner or a deferral — never "we'll see".
4 · Agent
Apply
Owner feeds the decisions back; the agent produces the consolidated artifact and re-validates (brd-builder Validate, prd-builder Validate, dependency re-check). Owner writes the decision log.
5 · Gate
Approve & baseline
Gate PR with the exit-criteria checklist in its body; named approver; merge to main; everyone pulls. The next lab starts from this file only.

Reconciliation meeting — agenda template (20 min)

0–2 minFrameOwner names the artifact of record and the exit criteria. Scrum Master shares the agent's five lists on screen.
2–8 minConflictsFor each: the two authors state their evidence in one sentence each. If both cite a line, both are true at different granularity — record both. If one has no source, it becomes an Assumption with a verification owner. Decision goes in the log as D-nn.
8–11 minDuplicatesKeep the lower ID; merge wording; carry the other's trace links; note the merge in the log. Never renumber.
11–14 minTerminologyThe glossary decides. Existing names in the code (quantity_in_stock, sale_date) beat invented synonyms; for new concepts the PO picks one word (manager, cashier, sign in).
14–17 minUnverified & unownedEvery unverified "fact" gets a person who will check app.py before the gate; every open question gets an owner and a target phase.
17–20 minCloseOwner reads the decision log back. Scrum Master confirms who approves the gate PR and when. Anything not decided is written down as not decided.
Ground rules that keep it short
  • Evidence, then opinion. A file path ends most arguments in ten seconds.
  • Agents prepare and apply; humans decide. Nobody says "the AI said so".
  • The owner of the artifact has the last word on wording; the Architect has the last word on technical conflicts; the PO on scope.
  • Disagreement that survives the meeting becomes an ADR alternative or an open question — never a silent default.

Strategies

Shared artifacts

One artifact of record per phase, in docs/, owned by one role. Working state stays in .copilot-tracking/ (personal, ignored). Promote by copying the distilled result, never the session state.

Git branches

Phase-prefixed branches (discovery/dev-code-evidence, adr/001-session-guard). One branch per contributor and phase; a reconciliation branch per phase owned by the phase owner; merge to main only at the gate. Never edit another role's file on your branch.

Pull requests

Small PRs per contribution, reviewed by a different discipline. The gate PR carries the exit-criteria checklist. Use /pull-request to draft PR descriptions from the diff and pr-review for a structured review; in Module 4, /ado-create-pull-request links the PR to its work items. Fact

Artifact ownership

PO: BRD, PRD, glossary, traceability. Architect: ADRs, diagram, security plan, dependency report. Scrum Master: backlog, triage, sprint plan. QA: validation strategy, DoD. Developers: code evidence, area decompositions, research + plans. Owners merge; others propose.

Conflicting assumptions

Tag them, quote both, decide in the reconciliation meeting, record in the phase decision log. An unresolved assumption becomes an open question with an owner and a target phase — never a silent default.

Duplicate requirements

Keep the lower ID, merge wording, add the other's trace links, note the merge in the decision log. Never renumber.

Inconsistent terminology

One glossary, owned by the PO, updated in every phase PR. The reconciliation prompt lists term drift; the glossary decides. Existing Stockroom column and route names win over invented synonyms.

Architecture disagreements

Both options go into the ADR with weighted drivers and consequences. The Architect decides; the PO confirms business fit; dissent is recorded. Reopening requires a new ADR that supersedes.

Dependency conflicts

Run the dependency-analysis prompt before unifying. Cycles are broken by re-scoping (usually schema or guard first). Duplicated ownership of a code area is resolved by the ADR that governs it.

Two trackers, one truth

Code and review live in the GitHub fork; work items live in Azure DevOps. Every ADO story carries the FR/AC IDs; every PR title carries the story ID (US-002) so /ado-create-pull-request can link them. Keep work-items.md in docs/ as the reviewable copy of the backlog.

Approval gates

Each phase names one approver and mandatory reviewers. AI outputs are inputs to the gate, never the gate. Baselines are immutable except by PR.

Best practices & gotchas

Practices the labs enforce

Do not jump from request to implementation

Run Method 1 (Scope Conversations) and repository research first. In this scenario the "obvious" implementation (a login form) misses who creates accounts, the shared tablet, the first-run bootstrap and the schema upgrade.

Separate facts, assumptions and decisions

Tag every line. An AI "fact" without app.py:line is an assumption. Decisions are recorded in ADRs or decision logs, not chat.

Require repository evidence for architectural claims

"Stockroom already has sessions" was true and misleading at once (app.py:15). "There is a migration mechanism" was false (app.py:39–68). The ADRs changed because someone looked.

Make acceptance criteria measurable

Binary, testable, one response per statement, numbers or binary conditions in NFRs. If a tester cannot say pass/fail, an agent cannot either.

Keep requirements technology-neutral until an ADR justifies a choice

"Must be performed by an identified person" in the BRD; "signed session + before_request guard" in ADR-001.

Record architecture decisions

Chat is not a system of record; ado-prd-to-wit and /task-plan read files, not conversations.

Maintain traceability

Stable IDs, links by ID, FR/AC IDs inside ADO acceptance criteria, one matrix owned by the PO. Section 13 shows the payoff.

Avoid giant work items

Story ≤ a week, task ≤ a day; split by system boundary; a story that needs its criteria split is a feature.

Explicitly model dependencies

By ID, both directions; run dependency analysis before unifying; schedule blockers first (schema, then guard).

Keep artifacts synchronized

One file per contributor per phase; reconcile on one branch; baseline on main; pull before the next lab.

Reconcile conflicting AI outputs before baselining

Two agents will disagree. Verify both against the repository; do not prefer the longer answer.

Humans approve important decisions

Named approver per phase; AI proposes, humans dispose. Fact HVE's own agents are built this way (read-only researcher, plan-only planner, backlog prompts that plan before they execute, partial autonomy by default).

HVE-specific gotchas from the official docs and repository Fact

  • Released names differ from the main branch docs. Installed 3.3.x uses /task-research, /task-plan, /task-implement, /task-review, ado-backlog-manager + /ado-* prompts, ado-prd-to-wit, arch-diagram-builder and prompt-builder.   • Collections, not one extension. hve-core alone gives you only the RPI agents; the builders, DT coach, security planner and ADO agents are separate extensions or hve-core-all. Overlapping installs yield duplicate agents.
  • .copilot-tracking/ is meant to be git-ignored — research, DT sessions, security plans, ADO planning files and task plans are not shared by default. Promote reviewed artifacts into docs/ deliberately.
  • Clear context between RPI phases and between ADO workflows. Task Researcher → /clear → Task Planner; planner session → /clear → execution. Findings are preserved in files, not chat history.
  • The Task Researcher always recommends one approach by design. When you want options for an ADR, ask for research only and move the recommendation into the ADR's alternatives.
  • The Task Planner calls the researcher if research is missing and treats every input as a planning request; it never implements.
  • rpi-agent's fifth phase is "Discover" (follow-up work), not lifecycle Discovery, and it needs a subagent tool enabled.
  • ADO agents plan first, execute separately. ado-prd-to-wit, /ado-discover-work-items, /ado-triage-work-items and /ado-sprint-plan write planning files; only /ado-update-wit-items (and /ado-add-work-item) mutate, with dryRun, partial autonomy gates, content sanitisation and resumption from handoff-logs.md.
  • ado-prd-to-wit plans Epic / Feature / User Story only (at most one Epic unless the PRD says otherwise); Feature needs an Epic parent, User Story needs a Feature parent. Tasks are yours to add.
  • The ADO MCP server is mandatory for every ado-* workflow (mcp_ado_core_get_identity_ids runs first). Keep either the github or the ado server configured, not both.
  • Content format: Azure DevOps Services uses Markdown, Azure DevOps Server uses HTML; pass contentFormat when detection is wrong.
  • Capacity is story points in ADO (unlike the GitHub prompts, where it is an issue count); set Microsoft.VSTS.Scheduling.StoryPoints or utilisation reads 0.
  • Agents load only when a folder or workspace is open, not a single file.
  • HVE lifecycle docs assign Discovery/Product Definition/Decomposition leadership to the TPM and mark the BPM guide beta; QA and Scrum Master are not native roles. Map explicitly (Section 06) and do not expect a "qa-agent".
  • DT Coach never prescribes solutions; a prompt that contains a solution derails Method 1 (Scope Conversations).
  • EARS and Given/When/Then are not enforced by prd-builder in 3.3.x — ask for them explicitly; agile-coach does insist on binary, checklist-style acceptance criteria.
  • Stockroom specifics: one module, raw SQL, no migrations, hard-coded secret, no CSRF, no tests until Lab 0 adds them, debug on by default outside Docker, database in a named volume that survives docker compose down.

Key takeaways

The lifecycle is the product

Setup → Discovery → Product Definition → Decomposition → Sprint Planning is not paperwork; it is how three sentences from a shop owner become work that survives contact with a real codebase and an AI agent.

Product roles drive HVE, they are not consulted by it

The PO ran dt-coach, brd-builder and prd-builder; the Scrum Master ran the ADO planner; the Architect ran the ADRs. Engineers supplied evidence, not requirements.

Parallel → Evidence → Review → Reconcile → Approve → Baseline

Five people worked at once in every phase because each had a file, a branch and a reviewer, and because reconciliation was an explicit step with a meeting and a decision log.

Evidence beats plausibility

Sessions "existed" but could not be trusted; a migration mechanism "surely existed" but did not; the first account "would just be created" but had no path. Research and critique caught all three before a line of code.

HVE's own design enforces the gates

Research-only researcher, plan-only planner, ADO prompts that plan before they execute with partial autonomy and dry runs, review-only reviewers. Use the tool the way it is built and your process gets the gates for free.

Promote what matters

.copilot-tracking/ is personal; docs/ is the team's memory; Azure DevOps is the tracker's memory. Decide what to promote at every gate, and keep the IDs identical in all three.

InstructionAuto-applied guidance scoped by file glob, plus .github/copilot-instructions.md for the whole workspace.
RPIResearch → Plan → Implement → Review, each owned by a custom agent (Task Researcher, Task Planner, Task Implementor, Task Reviewer) reached by /task-research, /task-plan, /task-implement, /task-review. Clear context between phases.
rpi-agent / /rpiAutonomous orchestrator running Research → Plan → Implement → Review → Discover (follow-up work); requires a subagent tool.
Design Thinking (DT)Nine methods across Problem, Solution and Implementation spaces coached by dt-coach; exits hand off to task-researcher with confidence markers.
Method 1 — Scope ConversationsDT method for discovering the real problem behind a solution request.
BRD / PRDBusiness Requirements Document (solution-agnostic; brd-builder → docs/brds/) and Product Requirements Document (prd-builder → docs/prds/).
EARSEasy Approach to Requirements Syntax: ubiquitous, event-driven ("When…"), state-driven ("While…"), unwanted-behaviour ("If… then…"), optional-feature ("Where…"); one response per statement. A workshop convention, not enforced by HVE 3.3.x.
Given / When / ThenBehavioural acceptance-criterion triplet complementary to EARS.
ADRArchitecture Decision Record: context, drivers, options, decision, consequences; docs/decisions/YYYY-MM-DD-topic.md.
STRIDEThreat categories (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) used by security-planner.
ado-backlog-managerOrchestrator agent behind the nine /ado-* prompts (discover, triage, sprint-plan, update-wit-items, add-work-item, get-my-work-items, process-my-work-items-for-task-planning, get-build-info, create-pull-request); plans into .copilot-tracking/workitems/ and executes only from a reviewed handoff. GitHub/Jira equivalents: github-backlog-manager, jira-backlog-manager.
ado-prd-to-wit"AzDO PRD to WIT" agent: analyses a PRD and plans an Epic → Feature → User Story hierarchy into work-items.md + handoff.md; never creates items itself.
HandoffThe checkbox list of planned tracker operations that the execution workflow applies; completed items are ticked, so re-running resumes.
Autonomy tierfull, partial (default) or manual — how many confirmation gates the backlog prompts apply before mutating Azure DevOps.
product-manager-advisor / agile-coachRequirements-discovery gate, story quality (story-quality.instructions.md) and prioritisation guidance; conversational story creation and refinement with binary acceptance criteria.
Completeness dimensionsUser, problem, evidence source, success criteria, acceptance criteria, dependencies, scope boundaries — the readiness rubric in story-quality.instructions.md.
.copilot-tracking/Git-ignored folder where HVE workflows persist state and artifacts.
PromoteWorkshop term: copy a reviewed artifact from .copilot-tracking/ into versioned docs/ for review and baselining.
BaselineThe approved artifact of record on main that the next phase consumes.
GateThe human approval step at the end of a phase, with a named approver and exit criteria.
Definition of Ready / DoneEntry and exit criteria for sprint items (DoR from completeness dimensions + traceability; DoD from tests, review, docs).
StockroomThe workshop application: an open-source small-business inventory & sales (POS) web app — Flask 3.1, SQLite via sqlite3, Jinja2 — by Bervely Pangwana (pangwanabervely-stack/stockroom-inventory-app).
Manager / cashierThe two roles decided in Discovery (D-02). A manager may delete products, open Reports and administer staff; a cashier may use everything else. "Owner" is a person who holds the manager role.
Guard (before_request)ADR-001's mechanism: a Flask hook that runs before every request, loads the current user into g.user, and redirects anything outside the allow-list to sign-in.
First-run bootstrapADR-002's path for creating the first manager account when the users table is empty (one-time setup page + CLI recovery).
Guarded ALTERADR-003's idempotent schema change: check PRAGMA table_info before ALTER TABLE sales ADD COLUMN recorded_by, because CREATE TABLE IF NOT EXISTS never alters an existing table.
